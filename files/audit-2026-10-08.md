## Findings

### 1. High — unpriced opening stock becomes free stock in the weighted average

**Evidence:** `src/lib/stock.ts:44,54-80`; `src/db/recipes.ts:223-250`; reproduced with the actual pure fold.

Create an ingredient, add 1 kg through a positive count correction without any purchase, then receive 1 kg at Rs 500/kg. The fold returns **Rs 250/kg** for the 2 kg now on hand. The adjustment leaves the initial average at zero; the first purchase includes that zero-valued quantity in the weighted numerator. The cost lookup now sees a purchase and accepts the resulting rate.

The original kilogram's cost is unknown. There is no evidence that it was free, and no honest combined average can be inferred from the new purchase alone. Every recipe using it can now receive an understated cost without an error.

**Fix direction:** explicitly retain whether existing positive stock has a valuation basis. Require a valued opening balance or reconciliation before treating the combined average as known. Preserve the single fold and append-only ledger; do not blindly substitute the latest purchase price for unknown historical value.

### 2. High — incomplete overhead is presented as a complete cost

**Evidence:** `src/db/recipes.ts:284-287`; `src/lib/costing.ts:104-117,296-297`; `app/recipes/[id]/cost/page.tsx:372-389`; nested case reproduced.

There are two reachable cases:

- Set labour to Rs 60/hour and leave kitchen overhead blank. The loader converts the missing kitchen rate to zero. A timed recipe reports overhead as applied and displays a zero kitchen charge, with no missing-rate warning. This contradicts the settings form's promise that blank is different from zero.
- Time the parent recipe but leave its dough sub-recipe untimed. The parent's flag says overhead is applied even though dough labour is missing. The visible warning checks only the parent's time. In the probe, Rs 1 of ingredients plus Rs 90 of parent overhead produces a Rs 91 total, while the child's overhead remains unknown and unflagged at the top level.

Also, `app/settings/costing/page.tsx:37-38` uses truthiness when loading inputs: an explicitly entered zero becomes blank and is saved back as null on an unchanged submission.

**Fix direction:** preserve null separately for each rate, propagate incomplete time/rate information from descendants, and label partial costs and margins accordingly. Use null checks when restoring zero-valued inputs.

### 3. High — changing a recipe's yield unit reinterprets existing menu portions

**Evidence:** `src/db/recipes.ts:443-455`; `app/recipes/actions.ts:174-216`; `app/recipes/menu-item-form.tsx:48-49,80-100`. Confirmed by tracing the write and display paths; database reproduction remains outstanding.

The yield-unit guard checks shelves and parent recipes, but not menu items. An unstocked recipe with no parent can change from a 1,000 g batch to a 10-unit batch while retaining a menu portion stored as 100,000 milli-base. That portion changes from **100 g to 100 units**. For a Rs 100 batch, its calculated portion cost changes from Rs 10 to Rs 1,000, although nobody edited the menu portion.

The menu form also displays a unit without submitting it, so a stale form cannot prove what unit the operator saw.

**Fix direction:** refuse yield-unit changes while menu portions depend on the recipe, or explicitly migrate those portions as a reviewed operation. Submit and validate the portion entry unit under the same concurrency guard as recipe edits.

### 4. Medium — the ingredient list displays an unknown price as Rs 0

**Evidence:** `src/db/ingredients.ts:81-87`; `app/ingredients/page.tsx:138-144`; also inspect the adjustment-only case in `src/db/history.ts:listLowStock`.

A newly created ingredient has no cache row. `toRow()` changes the missing rate into zero, and the ingredient table renders it as Rs 0.00 per purchase unit. An ingredient with adjustment history only also has a zero cache rate, without a valuation basis. The recipe lookup correctly refuses that ingredient, so different screens contradict each other about whether its price is known.

**Fix direction:** carry cost-basis status into ingredient and low-stock read models. Display “No cost recorded” for unknown values; show Rs 0 only for a genuine zero-valued purchase or production inflow. A nullable cache join alone does not cover adjustment-only stock.

### 5. Medium — a newly created production shelf can have its unit changed independently

**Evidence:** `src/db/ingredients.ts:184-223`; `src/db/production.ts:50-111,214-237`. Confirmed by source review; not exercised against PostgreSQL today.

After `stockRecipe()` creates an empty shelf, `updateIngredient()` sees no movements and no direct ingredient recipe lines. It therefore permits changing that shelf ingredient from weight to count. It does not inspect `recipes.stock_ingredient_id`. The recipe still yields grams, and its next production run writes those quantities into a shelf now displayed as units.

The recipe editor protects changes in the other direction, so this is a bypass through the ingredient editor.

**Fix direction:** treat a shelf link as a unit dependency even before the first movement. Coordinate the check with recipe stocking and ingredient edits so concurrent operations cannot bypass it.

### 6. Medium — very small production draws become illegal zero movements

**Evidence:** `src/lib/production.ts:188-190`; `src/db/production.ts:217-223`; `src/db/schema.ts:322`. The zero draw was reproduced; the database rejection follows from the checked-in constraint and was not executed today.

A line containing 0.001 g and a quarter-batch run produces an issued magnitude of zero after the approved rounding. The planner accepts it and the writer attempts a zero consumption movement. PostgreSQL rejects `stock_movements_qty_nonzero`, rolling back the whole run.

**Fix direction:** define the sub-resolution policy at the planner boundary. Either reject the run with a named, useful quantity error, or omit zero movements if that policy is explicitly accepted. Preserve exact signs and the one quantity rounding boundary.

## Concurrency issue requiring a database regression test

`loadRecipeGraphForTenant()` (`src/db/recipes.ts:84-123`) loads recipe headers and lines in separate queries. Normal read callers use the pool without a shared snapshot. A recipe save can commit between the reads, allowing an old yield to be combined with new ingredient quantities. For example, old yield 1 kg paired with the new inputs for a doubled 2 kg batch produces a doubled rate.

Production passes a transaction, but does not take the recipe graph lock used by `saveRecipe`; no stronger transaction isolation is configured. The loader comment claiming that a transaction alone prevents mixed versions is not a sufficient guarantee with the usual read-committed configuration.

This is a source-identified concurrency risk, **not a reproduced interleaving in this audit**. Add a forced-interleaving test before selecting a remedy. A single consistent graph read or appropriate locking can address it; do not casually change production isolation in a way that makes its post-lock price lookup stale.

## Supabase and Docker deployment options

Supabase can host this project's PostgreSQL database. The Next.js application still needs an application host. Keeping Drizzle and the existing server-side authentication is the smallest migration; changing to Supabase Auth or browser-direct database access is a separate project.

| Choice | What runs where | Handover trade-off |
|---|---|---|
| Existing Docker design | Next.js, PostgreSQL and Caddy on a client-owned VPS | Existing packaging; someone must maintain server, database and off-site backups |
| Managed app hosting + Supabase | Next.js on a managed Node/Next.js host; PostgreSQL on Supabase | Less server/database operations; two services, bills and account handovers |
| Docker app + Supabase | Next.js and Caddy on VPS; database managed separately | Reuses app packaging and removes local database operations, but VPS still needs maintenance |

For a handover with little ongoing server support, managed app hosting plus managed PostgreSQL is worth favouring. That is an architectural recommendation, not a verified deployment of this repository.

The current Docker path is already specified in `Dockerfile`, `.github/workflows/ci.yml`, and `deploy/docker-compose.prod.yml`: CI tests and builds app/migration images, publishes them to GHCR, and a VPS pulls a pinned `sha-` version. Compose starts PostgreSQL, runs migrations, starts the app, and puts Caddy in front for HTTPS. Nightly off-site backup and restore rehearsal complete the data handover. The automated deploy job remains commented out; simply uncommenting it is insufficient because its sample commands omit `-f docker-compose.prod.yml` and do not select the newly published image tag.

After server, DNS, secrets and image tag are prepared, the documented manual launch is:

```sh
docker compose -f docker-compose.prod.yml pull
docker compose -f docker-compose.prod.yml up -d
```

For Supabase, first rehearse all migrations and data import on a separate project, preserve runtime/migration role separation, check constraints/triggers/tenant isolation and replay invariants, then run every integration test without skips. Configure SSL, connection limits and pooling for the chosen application host. Persistent servers can use a direct connection or the session pooler; transaction pooling requires compatible driver configuration. [Supabase connection guidance](https://supabase.com/docs/guides/database/connecting-to-postgres), [Postgres.js guidance](https://supabase.com/docs/guides/database/postgres-js).

Keep database access behind the existing server authorization. Disable the Supabase Data API if it is unused, rather than unintentionally introducing another access path to the public-schema tables. [Supabase data security](https://supabase.com/docs/guides/database/secure-data).

Next.js supports Node hosting independently of Docker. Supabase documents automatic daily backups for Pro, Team and Enterprise projects; select the required retention/recovery arrangements and actually rehearse restoration before handover. [Next.js deployment](https://nextjs.org/docs/app/getting-started/deploying), [Supabase backups](https://supabase.com/docs/guides/platform/backups).

In either design, the client should own hosting, database, domain and billing accounts, with developer access granted separately. Deliver deployment/rollback instructions, a tested restore, and training for the actual staff workflows. No provider was provisioned or deployment configuration changed during this audit.
