## Defects reproduced outside the existing passing suite

All quantities and prices in these examples are fictional test fixtures, not cafe data.
The first seven were confirmed by pure and/or real database calls. The final two, and
the unknown-price display, were confirmed through the compiled app's HTTP forms.

| Priority | Defect | Observed consequence |
|---|---|---|
| High | Unpriced opening stock dilutes the first valued inflow | 1 kg of unknown value plus 1 kg bought at INR 500 produces a supposedly known INR 250/kg rate. |
| High | Missing overhead rate becomes zero | Stored NULL kitchen rate is loaded as zero and contributes no charge without retaining its unknown state. |
| High | Untimed sub-recipe overhead is not propagated as incomplete | A timed parent reports applied overhead and an INR 91 total while the child's labour/overhead is still unknown. |
| High | Recipe yield-unit changes reinterpret menu portions | Changing g to pieces is accepted with an existing portion; a former 100 g portion becomes 100 units, moving its calculated cost from INR 10 to INR 1000. |
| Medium | Unknown ingredient rate displays as zero | A never-purchased ingredient displays INR 0.00 while the costing lookup correctly refuses it as unpriced. |
| Medium | An unused production shelf can change measurement type | The ingredient editor accepts count while the linked producing recipe still yields weight. |
| Medium | Very small batch draws become illegal zero movements | A quarter batch with a 0.001 g line produces a raw `stock_movements_qty_nonzero` constraint error. Rollback is correct, but the operator does not get a useful quantity refusal. |
| Medium | Explicit zero overhead rates disappear on an unchanged save | Stored zeroes render as empty inputs; saving those inputs changes both stored values to NULL. |
| High | Receipt retries can duplicate a delivery | Submitting the same rendered receipt/payload twice creates two purchase movements. Clearing the client form after success is not server-side idempotency. |

Relevant implementations:

- `src/lib/stock.ts`, `src/db/stock.ts`, `src/db/recipes.ts`: opening valuation and cost lookup.
- `src/lib/costing.ts`, `src/db/recipes.ts`, `app/recipes/[id]/cost/page.tsx`:
  incomplete rate/time information.
- `app/settings/costing/page.tsx`: truthiness drops stored zero rates.
- `src/db/recipes.ts`, `app/recipes/actions.ts`, `app/recipes/menu-item-form.tsx`:
  menu-portion unit dependency and submitted-unit validation.
- `src/db/ingredients.ts`, `app/ingredients/page.tsx`: unknown-price read/display and
  linked-shelf unit dependency.
- `src/lib/production.ts`, `src/db/production.ts`: sub-resolution quantity policy.
- `app/stock/receipt/receipt-form.tsx`, `app/stock/actions.ts`, `src/db/movements.ts`:
  receipt submission identity and duplicate-write prevention.

## Repair order and acceptance

1. Keep unpriced stock and incomplete overhead explicitly unknown. A free sample
   recorded at zero must remain different from an unknown cost. Preserve the one
   ledger fold and the one costing implementation. Propose any necessary schema
   change before implementation.
2. Guard recipe/menu/shelf unit dependencies under the relevant locks. A menu portion
   form must submit the unit it displayed and have that claim verified server-side.
3. Give receipts a server-checked submission identity. Prove concurrent retries cannot
   create a second receipt, and handle a lost response without duplicate stock.
4. Preserve zero rates exactly in edit inputs, distinguish unknown rates in read models,
   and refuse sub-resolution production with a named domain error before writing.
5. Add desired-behaviour regressions for the failures above, demonstrate that each
   fails before its fix, rerun the native suite and HTTP workflows, then repeat the
   affected browser interactions with staff.

Production-run correction/undo and unstocking remain unimplemented. The workbook still
has unresolved measurements; the last reconciliation listed 225 pending entries. Actual
opening stock, purchase costs, selling prices and batch times still require cafe input.
This QA run did not invent any of those for the real cafe.

## Restore handover clarification

The restore utility uses `--no-owner --no-acl`. Restored row counts and append-only
triggers do not by themselves prove that the web app can read the restored database.
After restoring to the separate target, run the existing migrator using that target's
administrative connection and runtime password to reapply runtime grants; then test
the restricted role. This was done on both local restore targets and passed. Never
reuse the source URL as a restore target or change the live app connection for a rehearsal.
