# No Meat Naan — audit, 26 September 2026

Follow-on to [audit-2026-09-16](audit-2026-09-16.md). That audit closed nine findings the
same day. This one re-read every file under `src/` and `app/` against the rules AGENTS.md
states, checking claims against the configuration rather than against the comments.

Unlike the previous two, **the fixes below were applied in the same pass**, so this file
records both. The findings are left as they were written; an audit that edits itself once
the work is done stops being a record of what was wrong.

| | Before | After |
|---|---|---|
| Tests | 177 pass, 0 skipped | **194 pass, 0 skipped** |
| Tests over `app/` | **0** | 9, via extraction to `src/lib/form.ts` |
| `npm run typecheck` | pass | pass |

## 1. The client could not have logged in to the demo box — BLOCKING

`startSession` set the session cookie with `secure: process.env.NODE_ENV === 'production'`.
`deploy/docker-compose.prod.yml` sets `NODE_ENV=production`, and the demo runbook in
deploy/README.md uses `SITE_ADDRESS=:80` — plain HTTP on a bare IP.

**A browser refuses a `Secure` cookie sent from an `http://` origin.** localhost is the
only exemption, which is exactly why nobody saw it: every test of this ran on localhost.
The owner in Aurangabad would have signed in, been redirected, and landed back on the
login page with no error to read, indefinitely.

The two failure directions are not symmetric, which is what makes `NODE_ENV` the wrong
question: dropping `Secure` on an HTTPS site exposes the cookie, while setting it on an
HTTP site locks everybody out.

**Fixed.** The flag now follows `x-forwarded-proto`, which Caddy overwrites with the real
scheme, falling back to `NODE_ENV` when there is no proxy. Serving TLS is still the right
answer, and a hostname gets it free from Caddy.

## 2. The per-source login throttle could be walked straight past

`clientIp()` reads the **leftmost** `X-Forwarded-For` entry. Caddy's default is to
**append** the real client address to whatever arrived, and the Caddyfile set no
`header_up` or `trusted_proxies` — so a request carrying a forged header reached the app
as `<forged>, <real>` and the leftmost value was the attacker's. Rotating it defeated the
30-per-15-minutes source limit entirely.

The 8-per-account limit still held throughout, and that is the one standing between a
guesser and the owner's password.

The existing comment reasoned about who can *connect* to the app, which was true and not
the question — the header travels through the proxy intact regardless.

**Fixed.** The Caddyfile now pins `header_up X-Forwarded-For {remote_host}`, and
`X-Forwarded-Proto {scheme}` beside it because finding 1 now depends on it.

## 3. The throttle's own counters were unbounded

A key in `attempts` was pruned only when that same key came back. Nothing swept expired
ones, and guessing addresses is free — so "distinct emails ever tried" is
attacker-controlled, and the map that exists to bound an attack grew without bound.

**Fixed.** A sweep runs on the way in, above 10,000 tracked keys. Two tests, and the
guard was verified by disabling it and watching both go red.

## 4. One structurally broken recipe would have blanked the whole catalogue

`loadRecipeGraph` excludes soft-deleted recipes but keeps the lines pointing at them, so
`rateOf` hit `ctx.recipes.get()` returning undefined and threw
`Recipe <uuid> is not in the graph being costed`. `listRecipes` caught `MissingCostError`
and rethrew everything else, so that one recipe took out the recipe list and the home
page — the same failure the 16 September audit described for cycles.

Latent only because nothing can delete a recipe yet. It arrives the day that does.

**Fixed.** A named `MissingSubRecipeError` that names the parent to go and edit, and
`listRecipes` now carries a structural refusal as a value on that row rather than a throw.
The home page renders the reason instead of an empty ingredient list. Skipping the line
was considered and rejected: it would cost the parent as though the component were free,
which is AGENTS.md § Missing cost data is an error, never zero.

## 5. `saveRecipe` was the only writer that left the tenant out of its `WHERE`

Two statements filtered on id alone. `ingredients`, `users` and `menuItems` all filter on
both. Not exploitable — `graph.has(input.id)` proves ownership above — but non-negotiable
3 says every query filters by tenant, and a guard that lives in one place is one refactor
away from being the guard that *used to*.

**Fixed.** Both now carry `tenant_id`.

## 6. `consumption` was labelled "Sale" on the movement history

For a cafe whose manager logs materials used to *make* things, a consumption movement is
a batch being produced far more often than an item being sold.

**Fixed.** It reads "Used".

## 7. Changing an ingredient's unit type silently reinterpreted its whole history

`updateIngredient` applied `unitType` with no guard. A recipe line carries no unit of its
own — deliberately, the unit belongs to the source — so flipping weight to volume turns
"800 g of flour" into "800 ml of flour" everywhere, with no line re-validated. The ledger
is worse: stock on hand and the weighted average were accumulated in grams and
paise-per-gram and are afterwards read as millilitres and paise-per-millilitre. Nothing
throws, every figure still looks reasonable, and each one now means something else.

AGENTS.md named this hole and called it less severe on the grounds that no total moves.
That is true and understates it: the numbers hold still while the thing they measure
changes underneath them.

**Fixed**, in the same shape as the yield-unit guard `saveRecipe` already had. Narrow on
purpose — an ingredient with no movements and no recipe lines is still free to change,
which is the case where somebody is correcting a typo. Three tests, and the guard was
verified by disabling it.

## 8. The date filter dropped rows its own type said it kept

`HistoryFilter.to` is documented **exclusive**; `listMovements` compared it with `lte`,
and the page passed `23:59:59.999`. A JavaScript `Date` reaches milliseconds and a
Postgres `timestamptz` carries microseconds, so a movement written at `.9996` sat above
an inclusive bound built from a Date and silently fell outside a range the operator
believed covered it. On an append-only ledger that is the quiet-wrong-number class.

**Fixed.** Half-open, which has no gap at any precision, and the implementation now
matches the contract the type already stated.

## 9. The day boundary was computed in two places, and the timezone in four

`src/lib/time.ts` opens by calling itself "the one place a day boundary is computed", and
the history page had its own pair of helpers with `+05:30` written out again. Three pages
each built an `Intl` formatter around a hardcoded `'Asia/Kolkata'`.

Meanwhile `tenants.timezone` and `tenants.currency` are read by **nothing**.

**Fixed.** `TIMEZONE`, `istDayStart` and `istDayAfter` live in `time.ts` and the pages
import them. The two columns stay, with a comment saying plainly that they are unread and
why — one outlet, one zone, one currency — so the next reader does not wire them up and
find four display paths that disagree. Four tests.

## 10. Nothing under `app/` was tested at all

All 177 tests sat in `src/`. The claim in README that "every server action is tested at
the function layer" is true of the function an action *calls* and not of the action: the
Zod schemas, the indexed-FormData parser, the blank-row rule, the stale-pack refusal and
the sign-from-direction logic had no coverage. README's own handover says that is where
undiscovered defects are, and it was right.

A `'use server'` module may only export async functions, so nothing inside one can be
imported by a test. That is the mechanical reason this went uncovered.

**Fixed.** The two pure pieces moved to `src/lib/form.ts` and both actions import them.
Nine tests, including one pinning the hostile-index defence.

**And it immediately found a real bug.** The two copies of the row collector had diverged:
the recipe one filtered blank rows with `r.sourceId?.trim() !== ''`, which is **true** when
the key is absent, because `undefined !== ''`. A row submitting only its defaulted wastage
value survived as half-filled and failed with a message about picking an ingredient the
operator had never been shown. One collector now, and a test for exactly that.

## 11. Unbounded numeric input — measured, and smaller than it looked

Every text field carried a `.max()`; none of the numeric strings did, and they feed
`parseDecimalToInteger`, which does unbounded `BigInt` work. Measured before reporting: a
1 MB payload of digits costs about **141 ms**, and the route is authenticated. A
consistency gap rather than a denial of service.

**Fixed** anyway, at 24 characters — past any real entry.

## 12. `recordMovements` assumed one tenant without checking

The audit row is written with `lines[0].tenantId` for the whole group. Nothing builds a
mixed batch today, but this is the only door into the ledger and the invariant was assumed
from the callers that happen to exist.

**Fixed.** Asserted where it is relied on.

## 13. `integerToDecimal` truncates on a pack with an odd factor — verified unreachable

A tray of 30 gives scale 30000, and ten eggs is a third of a tray: no finite decimal
exists, so the display truncates at nine places and feeding that back fails as "more
precise than this field can store exactly" — about a field the operator may never have
touched. Carried over from the 14 September report.

**Checked rather than assumed.** Every route into a stored quantity converts the
operator's decimal against the pack size submitted *with* it, so the result always
divides; a query over the cafe's live 133 ingredients found **no value this cannot render
exactly**. The gap opens only if an importer or migration writes one directly.

**Not otherwise changed**, because every fix costs real UX for a case that cannot happen.
The ceiling is now written on the function, naming the two escape routes (store a multiple
of the pack, or move that field to base units where the scale is 1000 and everything
round-trips), and a test pins the behaviour so it is not a surprise later.

## Still open — the one that is not a defect

**The system cannot record materials used.** `consumption` is in the movement enum, in the
audit map and in the history labels, and is written by **nothing**. Stock only ever goes
down by hand, through an adjustment or a wastage entry.

The stated purpose of this software is logging what is ordered *and used* each day. The
first half works. The second half is [production-tracking-2026-09.md](production-tracking-2026-09.md),
which is a schema proposal and not yet built — it changes `stock_movements`, so it wants
review before code depends on it, and it is several steps rather than one.

## Documentation corrected

- README and AGENTS.md said 165 tests. It is 193.
- AGENTS.md's permission table listed three of the six permissions that exist, and did not
  mention that **`kitchen` appears in none of them** — a kitchen account can sign in and
  reach nothing until Module 5. Worth knowing before handing anyone that role to test with.

## What is still genuinely good

Unchanged from the 16 September verdict, and worth repeating because this report is a list
of faults and gives the wrong impression on its own. The arithmetic is the strongest part
of the system: integer scales end to end, `BigInt` through every intermediate, one fold
shared by the incremental cache and a full rebuild, rounding once per recipe with P7
pinning the nested case. Missing purchase history raises a named error instead of becoming
zero. Append-only is enforced by a trigger *and* a separate runtime role. Stock writes take
a sorted advisory lock before the insert, with a regression test proven to fail without it.

Nothing in this audit touched any of that, because none of it was wrong.
